# OIP v0.6 state commitment synchronization

This document is part of OIP v0.6.1. [Conformance scope](conformance.md) defines the requirement key words. [Operations](operations.md) defines the operand positions.

## Operation extension

An operation added within wire version 6 MUST use the next opcode at the end of an existing family. The earlier opcodes retain their layouts and meanings. A receiver that does not recognize an opcode rejects its frame as INVALID_FORMAT without an effect, a retained outcome or consumption of the call identifier. A receiver that recognizes the operation but excludes it from its configured operation set rejects it as UNSUPPORTED_VERSION after canonical decoding and before source, signature and authority checks. A sender MUST use its configured set of operations accepted by the peer. The signed version 6 offer selects families and the other profile fields documented in [wire conformance](wire-conformance.md). The operation set is established out of band. Implementers MUST identify the specification version for their conformance claims and vectors.

`SyncCommitment` is opcode 7 of STATE_SYNC and is a recorded call. `CurrentCommitment` is opcode 9 of QUERY and reads a current observation. The earlier reference profile continues to identify the operations it accepts by its own specification version.

## Synchronization call

The receiving authority maintains a state commitment for each registered pair of asset and origin domain. Each retained entry contains the 32-byte commitment, source position, origin epoch and origin event. The source position is an unsigned 64-bit integer, strictly increasing within this stream even across source signing epoch changes. A source position, an origin event identifier, a caller-qualified call identifier, a transport UUID and the receiver's authoritative revision have distinct meanings.

`SyncCommitment` carries ten words in order `message_reference`, `call_sequence`, `session`, `revision`, `origin_epoch`, `origin_domain`, `origin_event`, `asset`, `source_position`, `mode`. The signed cut is the Core authority epoch and the `revision` word. The Core target is the receiving authority. The Core source and principal identify the authenticated caller. The caller's domain can differ from the attested origin domain under the receiver's authorization policy. The call carries exactly three blobs in order `commitment`, `predecessor`, `source_attestation`. `commitment` has exactly 32 bytes. `predecessor` has exactly 32 bytes for INCREMENTAL and is an empty blob for INITIAL or FULL_RESYNC. The deadline field is absent. The third blob is opaque during transport admission. An empty third blob reaches the fresh source attestation check.

| Mode | Word | Requirement |
| --- | ---: | --- |
| INITIAL | 1 | The stream has no retained entry. The attestation is a source snapshot. |
| INCREMENTAL | 2 | The stream has a retained entry. Both the signed source predecessor and the signed request predecessor equal its commitment. |
| FULL_RESYNC | 3 | The stream has a retained entry. The attestation is a source snapshot and the caller has the current FullResync grant for this asset and origin domain at this receiving authority. |

The reference receiver MUST enforce the currently registered caller's execution permission for the asset. The FullResync grant is an additional scoped grant of that current session and policy. Only the active policy supplies the grant. Ownership or possession of a prior session does not supply a FullResync grant. On handover, the chosen successor policy explicitly supplies the grants of active sessions. An absent grant in a restored policy represents an empty scope.

For a fresh authenticated call, the receiver MUST recheck the signed cut, permissions, exact attested fields and the current origin signing roster at the boundary that records the outcome. If an entry exists, the supplied source position MUST be greater than its retained position, including in FULL_RESYNC. A fresh successful call consumes the origin event within the synchronization operation's namespace. An origin event already used by a different successful call cannot authorize another write. A change to an origin event's bound fields cannot authorize a write. Calls on other streams cannot change this entry.

The receiver MUST return the retained outcome for an exact authorized retry at the same receiver authority epoch before evaluating a new cut, source position or proof. It MUST preserve the exact original canonical Core with the outcome. A different Core for the same caller-qualified call identifier cannot recover or replace that outcome. Current caller authority and transport admission remain mandatory on retries. Both `ExactReceipt` and correlated response handling apply to a synchronization call under their original authorization and matching rules.

The receiver MUST treat an incorrectly encoded request as an admission error. An unavailable authority source uses the existing recorded Unavailable result. An available source with a stale signed receiver cut uses Busy before evaluating the fresh attestation. The receiver then checks the attestation, mode and predecessor, and origin event and position in that order. The first failure records SOURCE_ATTESTATION_REJECTED, STATE_COMMITMENT_MISMATCH or STATE_COMMITMENT_STALE respectively. The three new rejection results carry no commit position, consume the call identifier and leave the stream and product values unchanged. A successful STATE_COMMITMENT_SYNCED commits the new entry, origin event, exact request outcome, and corresponding read projection in one selected durable record. The commit position is the signed revision before the effect. The effect advances the authoritative revision by one. The recorded outcome and its commit position are stable across recovery and retry.

## Source attestation

The format uses a dedicated signing domain and an explicit claim kind. Source signing roster registration is scoped by deployment, origin domain, origin epoch and roster identifier. The currently selected sync policy names the single current origin epoch and roster for a source. That selection is separate from the historical registries that verify retained terminal evidence. A source key rotation selects a new authorized roster without resetting the stream's source position.

For format 1 and claim kind 1, the signed bytes consist of ASCII `OIP`, NUL, ASCII `SOURCE-ATTESTATION`, NUL, then nine unsigned 64-bit big-endian words in order `format_version`, `claim_kind`, `deployment`, `origin_domain`, `origin_epoch`, `roster_id`, `asset`, `origin_event`, `source_position`. The next bytes are the 32-byte commitment, one predecessor presence byte `0` or `1`, and exactly 32 predecessor bytes when the presence byte is `1`. The signature list starts immediately after this signed statement. It consists of an unsigned 64-bit big-endian count followed by that many records of an unsigned 64-bit big-endian signer identifier and a 64-byte Ed25519 signature. The signer identifiers MUST be strictly ascending. The list MUST end at the end of the proof blob. An unsupported format or claim kind is rejected.

The receiver MUST verify every supplied signature over the same statement bytes, with the current registered keys and strict Ed25519 verification. Signers and their registered public keys MUST be distinct and meet the registered nonzero quorum. The receiver MUST compare the statement deployment to the Core deployment, and its asset, origin domain, origin epoch, origin event, source position, commitment and predecessor to the matching request values. A predecessor presence byte of `0` denotes a snapshot. The request envelope separately signs the receiver's target, call identity, signed cut, mode and complete proof blob.

A reference source signer obtains the attested commitment, position, origin event and any predecessor from the current authenticated selected source record. Signers must read the exact same selected record to supply signatures for a quorum. Reopening the selected source retains its monotone positions and authenticated predecessor information. Authenticated storage and the truth of the source's external observations are supplier conditions.

## Current observation

`CurrentCommitment` carries four words in order `session`, `revision`, `asset`, `origin_domain`. Its deadline is absent and it has no blobs. The receiving authority MUST check the authenticated caller's read permission for this exact asset and origin at the same boundary that checks the current cut and reads the selected entry. The reference supplies its current observation through the host observation interface, with the authoritative revision and epoch and an optional commitment entry. An absent entry and a present 32-byte zero commitment are distinct. An unauthorized or stale query cannot return the value or its presence. This query observes the committed synchronization stream at the selected receiver and does not read the pending financial effect or locked application value. Go's message layer decodes the request and checks the transport conditions of its configured receiver.
