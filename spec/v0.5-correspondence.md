# OIP v0.5 correspondence

This document is part of OIP v0.6.1. It records how this version treats the items of the public OIP v0.5 documents. [Conformance scope](conformance.md) defines the requirement key words.

## Legacy path

The reference legacy codec is a reference compatibility record. It does not interoperate with the wire format of the public v0.5 documents.

## Items of the v0.5 documents

Each row gives the v0.5 item, its treatment in this version and where this version defines it. "Replaced" means this version defines a different mechanism for the same purpose. "Not defined" means this version contains no mechanism for the item.

| v0.5 item | Treatment | This version |
| --- | --- | --- |
| Version string in SemVer form | Replaced. The core carries the integer version 6, and peers negotiate the version per channel. | [Version check](wire-conformance.md#version-check-and-unknown-fields) |
| Timestamps in ISO 8601 | Replaced. Times are unsigned UTC seconds since the Unix epoch in fixed64 fields. | [Canonical signed message](wire-conformance.md#canonical-signed-message) |
| Chain identifiers in CAIP-2 form and display addresses | Replaced. Domains, principals and assets are registered 64-bit handles. | [Canonical signed message](wire-conformance.md#canonical-signed-message) |
| Seven message type discriminators | Kept. Family codes 1 to 7 keep the v0.5 message type numbers and names. | [Canonical field numbers](wire-conformance.md#canonical-field-numbers) |
| Canton origins and the Canton driver attestation fields | A Canton origin uses a registered domain handle. State commitment synchronization has a domain-neutral source statement. See the field correspondence below for the Canton profile. | [Canton driver attestation field correspondence](#canton-driver-attestation-field-correspondence) |
| GOVERNANCE message type | Changed meaning. Family 7 carries owner handover and authorized epoch installation. Registry, routing table and party mapping changes are not wire operations. | [Operations](operations.md) |
| Wire format and field numbers in a `.proto` schema | Defined. | `proto/oip.proto`, [Canonical field numbers](wire-conformance.md#canonical-field-numbers) |
| Public repository with code generation scripts and version history | Defined. The generation scripts are in `scripts/`. | `scripts/generate-wire.py`, `scripts/render-operations.py` |
| Self-check list as executable tests | Defined as conformance vectors that both language bindings run. | `tests/vectors/`, `scripts/test-wire-interop.py` |
| Message size limits and fragmentation | Size and nesting limits are configuration values of the receiving host. A frame over the limit receives INVALID_FORMAT, and a request whose response could exceed the limit is refused before effect. Fragmentation is not defined, so a message fits in one frame. | [Canonical signed message](wire-conformance.md#canonical-signed-message) |
| Procedure for new error codes and categories | A new assignment fixes its kind, commit presence, effect and retry rule. An older receiver uses its unknown-code rule. | [Response code allocation](response-code-extension.md) |
| Restricted DSL condition expressions | Not defined. The core carries no condition expression. | None |
| Routing registry records and updates ([v0.5 source](https://docs.oraclizer.io/oip-v05/routing/#dynamic-routing-table-updates)) | Changed mechanism. v0.5 populates ChainRegistry, AssetLocationMap, AuthorityRegistry and NodeRegistry through GOVERNANCE routing-table updates. This version takes registrations from host configuration and binds the selected policy fingerprint into retained authority state; those routing-table updates are not wire operations. A standalone signed registry-record encoding is not defined. | [Identity and ownership handover](identity-handover.md), [JSON policy binding](json-encodings.md#reference-signing-inputs) |
| Verifiable primary-finality preservation after lock expiry or reconciliation ([v0.5 invariant](https://docs.oraclizer.io/oip-v05/state-management/#pending-sync-queue-invariants)) | Partial scope. The reference binds primary decisions, pending source obligations, authoritative historical prefixes and secondary work into its durable authority state and authenticates exact recovery/archive inputs. A deployment-wide long-term archive policy, retention periods, compaction and storage tiers are not defined. The operational strategy remains open as recorded in [v0.5 Open Issues](https://docs.oraclizer.io/oip-v05/open-issues/#long-term-storage-strategy-for-primary-finality); an archive mechanism alone does not settle that policy. | [Authenticated persistence and recovery](persistent-recovery.md), [Primary decisions and publication](authoritative-outcomes.md) |
| Multi-Signatory authority field | A frame names one principal. The reference envelope uses SINGLE. State commitments can carry a separate source quorum statement. Owner handover requires the current owner and successor to consent separately. | [Identity and ownership handover](identity-handover.md), [Source attestation](state-commitment-sync.md#source-attestation) |

## State synchronization and wire scope

| v0.5 item | Treatment in version 6 | Definition |
| --- | --- | --- |
| StateSyncPayload with a full state body or per-field delta | The synchronization call records a 32-byte commitment with an authenticated source position and optional signed predecessor. An application defines the data represented by the commitment. A portable schema for the complete state body or its fields is reserved for a later version. | [State commitment synchronization](state-commitment-sync.md) |
| `currentStateHash` and state-hash mismatch | Requests execute against the signed authoritative cut. The synchronization call additionally compares its predecessor to the retained stream commitment. The corresponding recorded refusal is STATE_COMMITMENT_MISMATCH. | [Synchronization call](state-commitment-sync.md#synchronization-call), [Response code allocation](response-code-extension.md) |
| Fragmentation | The earlier open-issues schedule grouped fragmentation with the version 6 wire work. The format in this version uses a single bounded frame. Chunking would need a separately specified assembly, authenticity and replay rule. | [Canonical signed message](wire-conformance.md#canonical-signed-message) |
| Acknowledgement variants, diagnostic body, extra query fields and heartbeat state | The version 6 layouts specify the fields and effects of each operation. Correlated responses carry an exact original call and typed status. A general diagnostic object, phase acknowledgements and the extra fields of the older query and heartbeat bodies are outside these layouts. | [Operations](operations.md), [Reference outbound Response](wire-conformance.md#reference-outbound-response) |
| Capabilities and Liveness | The core has their layouts. The reference sets up its profile out of band using signed offers and confirmation and refuses these deliveries. A negotiated operation set and recovery messages belong to a later version. | [Version coexistence](wire-conformance.md#version-coexistence), [Reference scope](conformance.md) |
| LOCK extension and escalation variants | Lock management defines discrete commands, explicit permission and generation checks, and product rules for cancellation, fencing and preemption. The earlier general EXTEND and ESCALATE messages have no equivalent opcode. | [Lock authority](lock-finality.md#lock-authority), [Operations](operations.md) |
| Write and authorized epoch installation | Write uses the fixed LOCK_MANAGEMENT operand layout and the DATA_UPDATED result. InstallEpoch has a core layout and is excluded from the reference wire acceptance set. Current owner handover uses a signed exact policy and session change. | [Operations](operations.md), [Atomic owner and session handover](identity-handover.md#atomic-owner-and-session-handover) |
| Timeout and inbound CorrelatedResponse | The core defines their layouts. The reference time boundary takes a trusted signed observation, and the caller checks a correlated response on its response-verifier path. The reference request receiver refuses these operations. | [Trusted reference time](regulatory-execution.md#trusted-reference-time), [Reference outbound Response](wire-conformance.md#reference-outbound-response) |
| Primary and secondary Core codes | The decoder admits primary codes 1 through 5 and preserves a present secondary value. Neither field grants an effect or gives a product name to its numbers. | [Canonical field numbers](wire-conformance.md#canonical-field-numbers), [Operations](operations.md) |
| Asset classes, BOND, DERIVATIVE and KYC fields | A wire asset is a registered handle. An amount is a number of the registered asset's base units. The registry and its application policies own asset classification, token type, units and KYC data. | [Conformance scope](conformance.md) |
| Wider amounts and cross-asset dependencies | The wire amount has a fixed 32-byte representation and the reference has a u64 product range. The signed global cut governs competing writes, and the product only reorders operations with compatible dependencies. Changes to these widths and the cut scheme belong to a later version. | [Conformance scope](conformance.md), [Parallel composition](parallel-composition.md) |

## Routing, signatures and operations

| v0.5 item | Treatment in version 6 | Definition |
| --- | --- | --- |
| Recipient sets, multi-target broadcast and relays that change processing | The reference applies one authenticated local delivery to the signed target. A linked authorized transformation is required when a hop changes processing. This version defines single-hop delivery. The routing table, network dissemination and selection of a destination belong to the configured host. | [Version coexistence](wire-conformance.md#version-coexistence) |
| Priority escalation, CRITICAL hierarchy and jurisdiction | Priority and atomicity are signed. Scheduling priorities are a host policy. The core requires current privileged authority and ALL_OR_NOTHING for CRITICAL, which the reference profile does not grant. A multi-level registry or jurisdiction hierarchy is a distinct policy design. | [Canonical signed message](wire-conformance.md#canonical-signed-message), [Refusal precedence](wire-conformance.md#refusal-precedence) |
| Interval, backoff, dead-letter queue, alerts and slashing | The protocol specifies which outcomes consume the call identifier, what is known about the effect and how to resolve or retry. Scheduling a retry, storing work in a dead-letter queue, alerting and determining sanctions belong to the host or its authority registry. | [Effect and retry by code](wire-conformance.md#effect-and-retry-by-code) |
| Native driver and alternate signature schemes | Version 6 defines SINGLE Ed25519 for the reference and a THRESHOLD core code for distinct current authorized signers with trusted quorum. The latter is a rule about quorum authorization. The v0.5 BLS aggregate encoding and ECDSA schemes have no verifier or wire encoding in this profile. | [Canonical signed message](wire-conformance.md#canonical-signed-message) |
| Expiring restrictions, scheduled execution or cancellation, liquidation variables and AuthorityClaim | The typed regulatory operations and spend forms define their own authoritative effects, authorization and cut. The additional v0.5 parameters have no operands in these layouts. An authorized UNFREEZE may implement a host's expiration policy. | [Regulatory execution](regulatory-execution.md), [Operations](operations.md) |
| Conditions and staged broadcast | There is no general condition expression or phase broadcast payload. Product prerequisites are the typed checks of a particular operation, and finality and retry are expressed through retained authoritative outcomes. | [Operations](operations.md), [Authoritative outcomes](authoritative-outcomes.md) |

## Canton driver attestation field correspondence

The domain-neutral source statement covers the origin facts used by a state commitment synchronization call. A Canton profile would supply the Canton-specific interpretation of its ledger references, verified claims and Party binding. The driver and registered identity service own verification and invalidation of those external facts.

| v0.5 field | Version 6 correspondence | Remaining profile work |
| --- | --- | --- |
| `driverId` | The Core carries the registered caller principal. Source evidence identifies its registered signing roster and signers. | Registration and custody belong to the host. |
| `driverVersion` | Source statements have an encoding version. Core `key_id` identifies a key and has a different meaning. | Driver software versions belong to registration metadata. |
| `driverSignature` | The request has a SINGLE envelope signature. State synchronization uses the separate domain-neutral source statement and its registered quorum. | Canton-specific signing policy is owned by the Canton driver profile. |
| `timestamp` | The Core carries UTC `issued_seconds` and TTL. The source position orders states independently of delivery time. | Interpretation of Canton ledger time belongs to the driver. |
| `transactionId` | Origin domain and event identify an origin, with a separate transport UUID for delivery and separate caller-qualified call identity. | The mapping from a Canton transaction identifier into an origin event needs a Canton profile. |
| `ledgerOffset`, `workflowId` | The state statement carries a domain-neutral monotone position. | The representation and meaning of Canton locations belong to that profile. |
| `verifiedClaims` | The source statement binds the claim kind, asset, commitment, source position and origin epoch. | Canton-specific legal and ledger facts require driver verification. |
| `partyMapping` | Registered caller identity and authority sessions bind the request. | Party proof format, mapping lifecycle and invalidation belong to the profile and the identity registry. |

A refusal leaves earlier terminal records and supply intact. Later secondary delivery failure leaves the primary committed result in place. [Regulatory execution](regulatory-execution.md), [Primary and secondary results](authoritative-outcomes.md#primary-publication-and-secondary-settlement) |
| [Escalation-chain enforcement](https://docs.oraclizer.io/oip-v05/state-management/#escalation-chain-enforcement) uses both RESTRICTED and prior FREEZE as descriptions of entry to SEIZE. | A completed FREEZE for that asset and its exact reference are required. RESTRICT does not supply that provenance. [Regulatory entry](regulatory-execution.md#regulatory-entry) |
| The [contract transition text](https://docs.oraclizer.io/oip-v05/state-management/#contractstatus-and-regulatory-action-coupling) describes both action-only TERMINATED transitions and automatic termination. It gives different paths for a confiscation under appeal. | The reference records particular regulatory states and receipts. CONFISCATE checks the current seizure and elapsed appeal deadline. Automatic contract termination and a generic DISPUTED state belong to the application contract. [Regulatory entry](regulatory-execution.md#regulatory-entry) |
| [Coherence and governance](https://docs.oraclizer.io/oip-v05/state-management/#cross-chain-coherence) and [fault tolerance](https://docs.oraclizer.io/oip-v05/fault-tolerance/) use different authorities for restoring SYNCED. The queue invariant list is partly in the diagram. | The reference authenticates the selected primary record and retains exact pending obligations. | [Validation](https://docs.oraclizer.io/oip-v05/validation/#the-eight-validation-criteria) and [FREEZE transitions](https://docs.oraclizer.io/oip-v05/state-management/#state-transition-rules) differ on a locked starting state. | The typed regulatory rules use the current authoritative state and the allowed operation's own predicates. A permitted RESTRICT on a reserved asset preserves its reservation. The operation table and current guard define the allowed cases. [Regulatory entry](regulatory-execution.md#regulatory-entry), [Operations](operations.md) |
| [Registry self-defense](https://docs.oraclizer.io/oip-v05/validation/#rwa-registry-self-defense) describes a registered OSS caller, and [Force Inclusion](https://docs.oraclizer.io/oip-v05/validation/#force-inclusion-path-equivalence) describes an alternate route. | All reference ingress routes must consume the same final authority checks. The reference does not grant that privilege. Scope expansion, escalation and jurisdiction belong to the configured application policy. [Version coexistence](wire-conformance.md#version-coexistence), [Refusal precedence](wire-conformance.md#refusal-precedence) |
| The [lock-state errors](https://docs.oraclizer.io/oip-v05/regulatory-actions/#action-parameters) and the [state matrix](https://docs.oraclizer.io/oip-v05/state-management/#state-transition-rules) do not give one mapping. | The code and its effect, commit presence and retry rule follow the typed operation and its exact outcome. The result table gives the nearest earlier category. [Effect and retry by code](wire-conformance.md#effect-and-retry-by-code) |
| [TTL tables](https://docs.oraclizer.io/oip-v05/message-protocol/#ttl-determination) and [fault tolerance](https://docs.oraclizer.io/oip-v05/fault-tolerance/#ttl-time-to-live) use different names and recommended values. Unknown delivery results require exact resolution before reissuing work. [Regulatory entry](regulatory-execution.md#regulatory-entry), [Reference outbound Response](wire-conformance.md#reference-outbound-response) |

## Error codes

v0.6 response codes are numbers grouped by kind. [Effect and retry by code](wire-conformance.md#effect-and-retry-by-code) gives the closest v0.5 code for each v0.6 code. The v0.5 codes with no listed counterpart have no v0.6 response code of their own.
